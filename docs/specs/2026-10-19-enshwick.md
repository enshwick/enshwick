# Enshwick: the loader, its API and the first mods

Enshwick is one project, as Forge is for Minecraft: a loader that runs inside
the game and an API that mods are written against, released together, with the
mods built on it in the same workspace. The design follows the
[practices study](../research/2026-10-19-rust-performance.md).

## What players see

```text
Enshrouded/                     or the dedicated server's folder
  powrprof.dll                  the loader
  mods/
    flame-altar-zones.dll       one DLL per mod
    flame-altar-zones.toml      its settings, written with defaults when missing
    survivors-per-altar.dll
    enshwick.log                    the loader's and every mod's log
```

Installing a mod is copying its DLL into `mods/`; removing it is deleting it.
The loader alone changes nothing in the game. A game update the loader does not
know leaves every mod off and the game vanilla.

## Crates

| Crate                    | Kind                   | What it is                                                                                        |
| ------------------------ | ---------------------- | ------------------------------------------------------------------------------------------------- |
| `crates/enshwick`        | lib                    | the API mods depend on: the ABI types and the safe layer over them                                |
| `crates/enshwick-loader` | cdylib, `powrprof.dll` | the loader: proxy exports, start-up, game build, reflection, hooks, mods, config, log, join check |
| `crates/keen-reflect`    | lib                    | reading the game's reflection data from its image                                                 |
| `mods/<id>`              | cdylib each            | one mod                                                                                           |

`enshwick` holds the ABI in a `no_std` module with no dependencies
(`enshwick::abi`), so its layout is checked in one place, and the safe layer
beside it. The loader depends on `enshwick` for the same types; a mod depends on
nothing else of ours. Pure logic a mod owns, such as zone geometry, stays inside
that mod's folder as a crate of its own when it deserves tests apart from the
game.

## Start-up

1. Windows loads `powrprof.dll` from the game's folder. `DllMain` fills the
   forwards to the system `powrprof.dll` and starts one thread; nothing else
   runs under the loader lock.
2. The thread identifies the game: server or client, and the build fingerprint
   (debug GUID and age). It opens the log.
3. It reads the game's reflection and checks the loader's build table against
   it. An unknown build: the log says so and nothing more happens.
4. It discovers `mods/*.dll`, loads each library, and reads its manifest through
   `enshwick_mod_query`, which has no side effects.
5. It resolves the mod set: ABI version, side (server, client, both),
   dependencies with version ranges, incompatibilities, order. A mod whose
   requirement is missing is skipped and the log says why; the others load.
6. It calls each mod's `enshwick_mod_init` in dependency order. A mod registers
   hooks, services and settings there, and nothing takes effect yet.
7. It arms every hook chain, then calls `enshwick_mod_ready`. On the client,
   steps 6 and 7 wait until the game runs, past Steam's DRM wrapper.
8. On the server it advertises the mod set for the join check; on the client it
   checks the server's mod set when joining.

## The ABI

Rules, each checked at compile time where Rust can check it:

- Every type that crosses is `repr(C)`; enums cross as `repr(transparent)`
  integers, so an unknown value is data, not undefined behaviour.
- `HostApi` and `Manifest` start with `size: u32`, `abi_major: u16`,
  `abi_minor: u16`. Fields are only ever appended. A mod built against an older
  minor works with a newer loader; a newer mod checks `size` before using a
  later field. A different major is not loaded.
- Strings cross as borrowed `(ptr, len)` valid for the call. Nothing allocated
  in one DLL is freed in another; longer-lived things are host-owned handles.
- Every function pointer is `extern "system"`. Nothing unwinds across the
  boundary: each side catches panics at its entry points, and an escaped panic
  aborts rather than corrupting the game.

Exports of a mod:

| Export                                     | When         | Does                                                  |
| ------------------------------------------ | ------------ | ----------------------------------------------------- |
| `enshwick_mod_abi() -> u32`                | first        | the ABI major the mod was built for                   |
| `enshwick_mod_query() -> *const Manifest`  | after        | static data: id, version, side, requirements, symbols |
| `enshwick_mod_init(api, handle) -> Status` | in order     | registers hooks, services, settings                   |
| `enshwick_mod_ready(api, handle)`          | after arming | starts background work                                |

The safe layer turns these into one macro and one trait, so a mod reads:

```rust
enshwick::declare_mod!(FlameAltarZones);

impl enshwick::Mod for FlameAltarZones {
    const MANIFEST: enshwick::Manifest = enshwick::manifest! { id: "flame-altar-zones", side: Both };

    fn init(load: &mut enshwick::Load) -> Result<Self, enshwick::Off> {
        let settings: Settings = load.settings()?;
        load.hook(enshwick::game::BUILDZONES_SERVER, add_zones)?;
        Ok(Self { settings })
    }
}
```

## Game addresses

Mods name game functions by symbolic ids (`npc.lookup`, `ecs.iterator_next`),
never by address, as SKSE's Address Library does. The loader's build table maps
each id to an address for every game build it knows, after checking the build
against the game's reflection; systems the reflection names resolve by name and
survive updates on their own. A mod may carry rows of its own for ids the loader
does not know yet, keyed by the same build fingerprint. An id with no address on
the running build turns off the mod that needs it, never the game.

## Hooks

A target, one game function, is detoured once, by the loader. Each mod's detour
is a link in that target's chain:

- A link gets the arguments and a `Next` it may call or not. `Next` is a static
  slot the loader points at the following link or at the original, so a call
  through it is one load and one indirect call.
- Links run in priority order, then in mod load order. A mod may declare a
  target exclusive; a second exclusive claim turns the later mod off.
- A detour is installed only for a target with at least one link, and arming
  happens once, after every mod's `init`.
- A link that needs the game's call site (the survivors mod tells callers of one
  lookup apart this way) declares it, and the loader's entry stub for that
  target records the caller's frame for the thread before the chain runs.
- A link that panics is caught at its boundary, its mod is marked faulted and
  every link of that mod is unlinked by repointing slots. No code is repatched
  while the game runs.

Rare events, such as a player joining or a save loading, go through an event bus
with priorities instead, so per-frame chains carry no event objects.

## Services between mods

A mod can publish a service, a named and versioned table of functions, and
another mod can require it like a dependency. The survivors mod requires the
altar zones service of `flame-altar-zones`, which today it reads through a
crate-internal call.

## Settings and log

Each mod's settings live in `mods/<id>.toml`. The loader hands the mod its text,
or writes the mod's defaults when the file is missing; the safe layer parses it
into the mod's own type with serde. Settings that peers must share are declared
as join values.

One log, `mods/enshwick.log`, written by a background thread from a lock-free
queue, so a hook never waits on the disk. Every line names its mod. Hooks log
once per event worth knowing, never per frame, and the safe layer rate-limits
per call site.

## Join check

The server advertises a fingerprint of its mod set: the loader version, and each
mod that declares itself part of the join with its version and join values. A
client with a different set gets a clear message before it joins.

## Performance

The release profile is `opt-level = 3`, fat LTO, one codegen unit,
`panic = "unwind"`, line tables only, with PDBs kept per release; the target CPU
is `x86-64-v2` and the CRT is static, so no redistributable is needed. Hot
paths, every link and per-frame pass, do not allocate, lock or log in the common
case, and their state is atomic, thread-local or swapped whole. The loader
counts calls per link, and the hooks with the most calls get benchmarks.

## The first mods

| Mod                   | What it does                                             |
| --------------------- | -------------------------------------------------------- |
| `flame-altar-zones`   | altar clusters, uniform growth, building across seams    |
| `flame-altar-count`   | the configurable table of altars per Flame level         |

checked on a test server before its first release.
